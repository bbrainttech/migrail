# MR201 · alter-column-type-rewrite

## What it detects

`ALTER COLUMN … TYPE` on a table that this change set didn't create.

## Why it's dangerous

Most type changes make Postgres rewrite every row and rebuild every index on the table. It holds an `ACCESS EXCLUSIVE` lock for the whole rewrite, so every query on the table waits. On a large table this takes minutes and needs disk space for a second copy of the table.

A few changes only update the catalog and finish at once. Examples are `varchar(n)` to `text`, raising a `varchar` limit, and raising `numeric` precision without changing the scale. migrail reads migrations, not the live schema, so it usually can't see the current type. When the new type allows a catalog-only change, migrail reports a warning with `possible` confidence instead of an error.

A `USING` clause that computes a value always forces a rewrite.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ALTER COLUMN … TYPE` | `ACCESS EXCLUSIVE` | all queries | rewrites the table and rebuilds its indexes |
| `ALTER COLUMN … TYPE` (catalog-only change) | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none |

These locks apply to PostgreSQL 12 through 18.

## How to fix

Use expand and contract:

1. Add a new column with the new type.
2. Write to both columns from the application and backfill the new column in batches.
3. Switch reads to the new column, then drop the old column and rename the new one.

```sql
ALTER TABLE orders ADD COLUMN total_new numeric(12, 2);
```

## When it's safe to ignore

- The change only updates the catalog, for example `varchar(50)` to `text`.
- The table is empty or very small in every environment.
- The migration runs during a maintenance window with traffic stopped.

## Examples

Bad:

```sql
ALTER TABLE orders ALTER COLUMN id TYPE bigint;
```

Good:

```sql
ALTER TABLE orders ADD COLUMN id_new bigint;
```
