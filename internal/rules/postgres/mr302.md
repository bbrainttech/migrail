# MR302 · rename-column

## What it detects

`ALTER TABLE … RENAME COLUMN` on a table that this change set didn't create.

## Why it's dangerous

A deploy doesn't replace the application at the same moment the migration runs. During a rolling deploy, instances running the previous release keep serving requests, and their queries still use the old column name. Those queries fail as soon as the rename commits. The same happens if the migration runs before the new release starts, or if you roll the release back.

The rename itself is fast. It takes an `ACCESS EXCLUSIVE` lock only for a moment.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `RENAME COLUMN` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none |

These locks apply to PostgreSQL 12 through 18.

## How to fix

Rename in three deploys with expand and contract:

1. Add the new column. Write to both columns from the application and backfill the new column.
2. Read from the new column and stop writing the old one.
3. Drop the old column.

## When it's safe to ignore

- No application code reads or writes the column.
- The application stops completely while the migration runs.

## Examples

Bad:

```sql
ALTER TABLE users RENAME COLUMN email TO email_address;
```

Good:

```sql
ALTER TABLE users ADD COLUMN email_address text;
```
