# MR205 · vacuum-full-or-cluster

## What it detects

`VACUUM FULL` and `CLUSTER` on tables that this change set didn't create, and on the whole database when no table is named.

## Why it's dangerous

Both commands write a complete new copy of the table and its indexes. They hold an `ACCESS EXCLUSIVE` lock the whole time, so reads and writes stop until they finish, and they need enough free disk space for a second copy.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `VACUUM FULL` | `ACCESS EXCLUSIVE` | all queries | rewrites the table |
| `CLUSTER` | `ACCESS EXCLUSIVE` | all queries | rewrites the table in index order |
| `VACUUM` | `SHARE UPDATE EXCLUSIVE` | other schema changes | marks space for reuse |

## How to fix

Rebuild the table online with the `pg_repack` extension, which only takes a brief exclusive lock at the end. If `pg_repack` isn't available, run the command in a maintenance window instead of a deploy migration.

## When it's safe to ignore

- The table is small.
- The migration runs during a maintenance window.

## Examples

Bad:

```sql
VACUUM FULL orders;
```

Good:

```sql
VACUUM orders;
```
