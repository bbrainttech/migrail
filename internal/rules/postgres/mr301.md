# MR301 · drop-column-in-use

## What it detects

`ALTER TABLE … DROP COLUMN` on a table that this change set didn't create.

migrail doesn't scan application code yet, so every dropped column is reported as a warning with `possible` confidence. Once code scanning ships, this rule reports an error only when code still uses the column.

## Why it's dangerous

During a rolling deploy, instances running the previous release keep reading and writing the column, and their queries fail once it's gone. ORMs that cache the column list, such as ActiveRecord, fail even for queries that don't name the column.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `DROP COLUMN` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none, the space is reclaimed later |

## How to fix

1. Remove every read and write of the column from the application. In Rails, add it to `ignored_columns`. In Django, remove the field with `SeparateDatabaseAndState`.
2. Deploy.
3. Drop the column in a later deploy.

## When it's safe to ignore

- No release that is still running uses the column.

## Examples

Bad:

```sql
ALTER TABLE users DROP COLUMN email;
```

Good: remove the application code first, then drop the column in a later release.
