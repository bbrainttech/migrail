# MR503 · delete-or-update-without-where

## What it detects

`UPDATE` or `DELETE` without a `WHERE` clause on a table that this change set didn't create.

## Why it's dangerous

The statement changes or deletes every row. It locks every row it touches until the transaction commits, so concurrent writes to the table wait. On a large table it also creates a dead copy of each row, which bloats the table until vacuum catches up.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `UPDATE` / `DELETE` without `WHERE` | `ROW EXCLUSIVE` on the table, row locks on every row | writes to every row | rewrites or deletes every row |

## How to fix

- Add a `WHERE` clause that limits the statement to the rows it should change.
- For a real full-table backfill, update rows in batches by primary key range, outside the schema migration.

## When it's safe to ignore

- The table is small and the change is intended for every row.

## Examples

Bad:

```sql
UPDATE orders SET status = 'archived';
```

Good:

```sql
UPDATE orders SET status = 'archived' WHERE created_at < '2024-01-01';
```
