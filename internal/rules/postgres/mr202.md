# MR202 · add-column-volatile-default

## What it detects

`ADD COLUMN … DEFAULT` with a volatile function, such as `gen_random_uuid()`, `random()` or `clock_timestamp()`, on a table that this change set didn't create. Defaults that call a function migrail doesn't recognize are reported as a warning with `possible` confidence.

## Why it's dangerous

Since PostgreSQL 11, adding a column with a constant or stable default only updates the catalog. A volatile default is different: every row needs its own value, so Postgres computes it for each existing row and rewrites the whole table under an `ACCESS EXCLUSIVE` lock.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ADD COLUMN … DEFAULT now()` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none |
| `ADD COLUMN … DEFAULT gen_random_uuid()` | `ACCESS EXCLUSIVE` | all queries | rewrites the table |
| `ALTER COLUMN … SET DEFAULT gen_random_uuid()` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none, applies to new rows only |

## How to fix

1. Add the column without a default.
2. Set the default, which only affects rows inserted from now on.
3. Backfill existing rows in batches.

```sql
ALTER TABLE orders ADD COLUMN token uuid;
ALTER TABLE orders ALTER COLUMN token SET DEFAULT gen_random_uuid();
```

## When it's safe to ignore

- The table is empty or very small in every environment.
- The function in the default isn't volatile.

## Examples

Bad:

```sql
ALTER TABLE orders ADD COLUMN token uuid DEFAULT gen_random_uuid();
```

Good:

```sql
ALTER TABLE orders ADD COLUMN token uuid;
ALTER TABLE orders ALTER COLUMN token SET DEFAULT gen_random_uuid();
```
