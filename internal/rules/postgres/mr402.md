# MR402 · concurrent-in-transaction

## What it detects

`CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `REINDEX … CONCURRENTLY` and `REFRESH MATERIALIZED VIEW CONCURRENTLY` inside a transaction, either after an explicit `BEGIN` or in a migration that the migration tool wraps in a transaction.

## Why it's dangerous

Postgres rejects these commands inside a transaction block with `cannot run inside a transaction block`. The migration fails when it runs, often only in the environment where the migration tool's transaction settings differ.

## Lock & impact

None. The statement fails before it does any work, and the migration's transaction rolls back.

## How to fix

Run the statement outside a transaction:

1. Move it to its own migration.
2. Turn off the migration tool's transaction for that migration, for example `-- +goose NO TRANSACTION`, `disable_ddl_transaction!` in Rails or `atomic = False` in Django. For plain SQL files, remove `BEGIN` and `COMMIT` around it.

## When it's safe to ignore

Never. The statement always fails inside a transaction.

## Examples

Bad:

```sql
BEGIN;
CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
COMMIT;
```

Good:

```sql
CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
```
