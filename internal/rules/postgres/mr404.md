# MR404 · not-valid-validate-same-tx

## What it detects

`VALIDATE CONSTRAINT` in the same transaction as the `ADD CONSTRAINT … NOT VALID` that created the constraint.

## Why it's dangerous

`NOT VALID` avoids a long lock by skipping the scan of existing rows. But the lock taken by `ADD CONSTRAINT` is held until the transaction commits. Validating in the same transaction scans the table while that lock is still held, so writes stay blocked for the whole scan, exactly as if `NOT VALID` had never been used.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ADD CONSTRAINT … NOT VALID` then `VALIDATE` in one transaction | the `ADD CONSTRAINT` lock, held during the scan | writes, or all queries for `CHECK` | scans the table |
| `VALIDATE CONSTRAINT` in its own transaction | `SHARE UPDATE EXCLUSIVE` | other schema changes | scans the table |

## How to fix

Keep `ADD CONSTRAINT … NOT VALID` in this migration and move `VALIDATE CONSTRAINT` to the next migration, or commit between the two statements.

## When it's safe to ignore

- The table is empty or very small in every environment.

## Examples

Bad:

```sql
BEGIN;
ALTER TABLE orders ADD CONSTRAINT orders_user_id_fkey FOREIGN KEY (user_id) REFERENCES users (id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_user_id_fkey;
COMMIT;
```

Good:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_user_id_fkey FOREIGN KEY (user_id) REFERENCES users (id) NOT VALID;
```

```sql
ALTER TABLE orders VALIDATE CONSTRAINT orders_user_id_fkey;
```
