# MR502 · drop-table

## What it detects

`DROP TABLE` on tables that this change set didn't create.

## Why it's dangerous

The table and all its rows are gone once the migration commits. If the drop was a mistake, the only way back is a backup. Code that still queries the table also fails during a rolling deploy.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `DROP TABLE` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | removes the table and its data |

## How to fix

Keep a way back until you're sure the data isn't needed:

1. Back up the table, or rename it instead of dropping it.
2. Remove every use of it from the application.
3. Drop it in a later migration.

## When it's safe to ignore

- The data is backed up or no longer needed, and no running code uses the table.

## Examples

Bad:

```sql
DROP TABLE invoices;
```

Good:

```sql
ALTER TABLE invoices RENAME TO invoices_to_delete;
```
