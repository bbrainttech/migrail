# MR105 · add-check-validating

## What it detects

`ADD CONSTRAINT … CHECK` without `NOT VALID` on a table that this change set didn't create.

## Why it's dangerous

Postgres checks every existing row against the new constraint while it holds an `ACCESS EXCLUSIVE` lock. Every query on the table, including `SELECT`, waits until the check finishes.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ADD CONSTRAINT … CHECK` | `ACCESS EXCLUSIVE` | all queries | scans the table |
| `ADD CONSTRAINT … CHECK … NOT VALID` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none |
| `VALIDATE CONSTRAINT` | `SHARE UPDATE EXCLUSIVE` | other schema changes | scans the table |

These locks apply to PostgreSQL 12 through 18.

## How to fix

Add the constraint as `NOT VALID`, which enforces it for new and updated rows right away. Then validate it in a separate migration.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_total_positive CHECK (total > 0) NOT VALID;
```

```sql
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_positive;
```

## When it's safe to ignore

- The table is empty or very small in every environment.
- The migration runs during a maintenance window.

## Examples

Bad:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_total_positive CHECK (total > 0);
```

Good:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_total_positive CHECK (total > 0) NOT VALID;
```
