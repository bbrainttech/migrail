# MR207 · add-column-not-null-no-default

## What it detects

`ADD COLUMN … NOT NULL` without a `DEFAULT`, identity or generated value, on a table that this change set didn't create.

## Why it's dangerous

Existing rows have no value for the new column, so Postgres rejects the statement with `column contains null values` as soon as the table has a row. On an empty development database the migration passes, and it fails in production.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ADD COLUMN … NOT NULL` | `ACCESS EXCLUSIVE` | all queries | fails if the table has rows |
| `ADD COLUMN … DEFAULT 'x' NOT NULL` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none for a constant default |

## How to fix

Either add the column with a constant default, or:

1. Add the column as nullable.
2. Backfill it in batches.
3. Set `NOT NULL` using a validated `CHECK` constraint first, as `migrail explain MR107` shows.

```sql
ALTER TABLE orders ADD COLUMN status text;
```

## When it's safe to ignore

- The table is empty in every environment, including production.

## Examples

Bad:

```sql
ALTER TABLE orders ADD COLUMN status text NOT NULL;
```

Good:

```sql
ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'pending';
```
