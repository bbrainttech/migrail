# MR403 · missing-lock-timeout

## What it detects

The first statement in a migration that locks an existing table, such as `ALTER TABLE`, `CREATE INDEX`, `CREATE TRIGGER`, `TRUNCATE` or `DROP TABLE`, when no `lock_timeout` is set earlier in the migration. It's reported once per migration.

## Why it's dangerous

A schema change has to wait for every query that holds a conflicting lock on the table. While it waits, it blocks every query that arrives after it, even ones that don't conflict with the running query. A long report query or an idle transaction can turn a millisecond `ALTER TABLE` into minutes of blocked traffic.

`lock_timeout` makes the statement give up instead of waiting, so the queue clears and the migration can be retried.

## Lock & impact

Depends on the statement. The risk is the time spent waiting for the lock, not the lock mode itself.

## How to fix

Set a lock timeout at the top of the migration, and retry the migration when it times out.

```sql
SET lock_timeout = '5s';
```

## When it's safe to ignore

- The database or role already sets `lock_timeout`. migrail only sees settings in the migration.
- The migration only touches tables that nothing else uses.

## Examples

Bad:

```sql
ALTER TABLE orders ADD COLUMN note text;
```

Good:

```sql
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN note text;
```
