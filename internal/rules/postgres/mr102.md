# MR102 · drop-index-non-concurrent

## What it detects

`DROP INDEX` without `CONCURRENTLY`, unless the index was created earlier in the same change set.

## Why it's dangerous

`DROP INDEX` takes an `ACCESS EXCLUSIVE` lock on the table the index belongs to. The drop itself is fast, but it has to wait for every query that is using the table. While it waits, every new query on the table queues behind it, so one long-running query can stall the whole table.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `DROP INDEX` | `ACCESS EXCLUSIVE` on the table | all queries | removes the index files |
| `DROP INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` on the table | other schema changes | waits for queries using the index to finish |

These locks apply to PostgreSQL 12 through 18.

## How to fix

Drop the index concurrently. `DROP INDEX CONCURRENTLY` can't run inside a transaction, drops one index per statement and doesn't support `CASCADE`.

```sql
DROP INDEX CONCURRENTLY idx_orders_status;
```

## When it's safe to ignore

- The table is small and has little traffic.
- The migration runs during a maintenance window.

## Examples

Bad:

```sql
DROP INDEX idx_orders_status;
```

Good:

```sql
DROP INDEX CONCURRENTLY idx_orders_status;
```
