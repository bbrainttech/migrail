# MR106 · add-unique-constraint-blocking

## What it detects

`ADD CONSTRAINT … UNIQUE` or `ADD PRIMARY KEY` that builds its own index, on a table that this change set didn't create. Constraints added with `USING INDEX` are fine. Unique constraints declared inline on `ADD COLUMN` aren't detected yet.

## Why it's dangerous

Postgres builds a unique index for the constraint while it holds an `ACCESS EXCLUSIVE` lock. Every query on the table waits for the whole index build.

## Lock & impact

| Statement | Lock | Blocks | Work |
|---|---|---|---|
| `ADD UNIQUE` / `ADD PRIMARY KEY` | `ACCESS EXCLUSIVE` | all queries | builds an index |
| `CREATE UNIQUE INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` | other schema changes | builds an index |
| `ADD CONSTRAINT … USING INDEX` | `ACCESS EXCLUSIVE`, briefly | all queries, only for a moment | none |

For `PRIMARY KEY`, Postgres also sets `NOT NULL` on the key columns, which scans the table if they allow NULL. Set `NOT NULL` first using the pattern in `migrail explain MR107`.

## How to fix

Build the unique index concurrently, outside a transaction, then attach it to the constraint.

```sql
CREATE UNIQUE INDEX CONCURRENTLY orders_code_key ON orders (code);
```

```sql
ALTER TABLE orders ADD CONSTRAINT orders_code_key UNIQUE USING INDEX orders_code_key;
```

## When it's safe to ignore

- The table is empty or very small in every environment.
- The migration runs during a maintenance window.

## Examples

Bad:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_code_key UNIQUE (code);
```

Good:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_code_key UNIQUE USING INDEX orders_code_key;
```
