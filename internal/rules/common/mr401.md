# MR401 · edited-applied-migration

## What it detects

A migration file that already exists on the base branch and was modified in the current change, compared with the git merge base.

## Why it's dangerous

Migration tools record which migrations ran and never run them again. A database that already applied this migration keeps the old version, while a new database, such as a fresh test environment, gets the edited one. The schemas drift apart and nothing reports an error until something breaks.

## Lock & impact

None directly. The risk is environments that no longer match.

## How to fix

1. Revert the changes to the applied migration.
2. Put the change in a new migration.

Whitespace or comment-only edits are harmless. Ignore the finding with a reason if that's all that changed.

## When it's safe to ignore

- The migration hasn't run anywhere yet, for example it was merged minutes ago and never deployed.
- The change only touches comments or whitespace.

## Examples

Bad: editing `20260101000000_create_orders.sql` after it was merged.

Good: adding `20260917101500_add_orders_status.sql` with the change.
